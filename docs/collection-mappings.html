go-virtual / Collection Mappings

Collection Mappings

Collection Mappings let you read and write structured data inside the session store using familiar database-style operations — insert, find, update, delete — without writing a single line of Starlark. Map request fields directly to collection documents and inject the results into your response templates and conditions.

How It Works

Collections are lightweight tables inside a client's session store. Each session gets its own private namespace of collections. A Collection Mapping is a rule that tells go-virtual: "for this request, run this operation against this collection and store the result under this key."

Collection Mappings are the no-code path to stateful mocking. Instead of writing a Starlark script to insert a user record and return it, you configure a mapping rule in the UI — no code required.

💡
Session required Collections are stored inside the client's session. The client must send the X-Virtual-Session-Id header (or whatever header name is configured). If no session header is present, collection write operations are silently skipped.

Request pipeline position

At each scope, scripts, validation rules, and collection mappings execute together in a single mixed-order pipeline, interleaved by their order field rather than running in fixed phases. You control the exact sequence by setting the order on each step.

StepWhat happens
① RoutePath + method matched to an OpenAPI operation
② SessionSession resolved from header
③ Recorded responsesSignature-matched pre-recorded responses served immediately
④ Spec-scope pipelineScripts, validation rules, and collection mappings at spec level run in user-defined order. Results accumulate and are visible to later steps in the same pipeline.
⑤ Proxy checkProxy mode evaluated using spec-scope outputs
⑥ Operation-scope pipelineScripts, validation rules, and collection mappings at operation level run in user-defined order. Results merge with spec-scope outputs.
⑦ Response matchResponse configs evaluated in priority order; conditions can reference all script, validation, and collection outputs
⑦.5 Response-scope pipelineScripts and collection mappings at response level run in user-defined order after a config is matched. Validation rules are not supported at response scope.
⑧ Template renderResponse body + headers rendered with full context from all scopes

Because spec and operation-scope pipelines run before response matching (steps ④ and ⑥), you can use their collection results in conditions to select different responses. Response-scope mappings run after matching (step ⑦.5) — ideal for side-effect writes like recording the request in a log collection.

💡
Ordering across step types Use the Pipeline panel on the Spec Detail or Operation Detail page to drag and reorder all steps — scripts, validation rules, and collection mappings — in a single unified view. Within a scope, a step with a lower order number runs first. Steps with equal order numbers run scripts before validations, validations before collections.

Scopes: Spec, Operation & Response

Every Collection Mapping belongs to exactly one scope, determined by where you create it:

📄
Spec Level
Created on the Spec Detail page. Runs for every request to any operation in this spec. Use for cross-cutting reads — for example, loading the current user document from a users collection before any response is chosen.
🔗
Operation Level
Created on the Operation Detail page. Runs only for requests matching that specific operation. Great for operation-specific reads, such as looking up a product when only the GET /products/{id} operation is called.
📨
Response Level
Created in the Response Config editor. Runs only when this specific response config is matched. Ideal for side-effect writes — for example, inserting a record when the "create user" response is served.

Merge priority

When multiple scopes produce an output with the same key, response-level wins over operation-level, which wins over spec-level. This lets you override general behavior with more specific handling without touching higher-level mappings.

Collection Operations

Each mapping performs one of six operations against the named collection in the session store:

OperationDescriptionUses Filter?Uses Data?
find-oneReturn the first document matching all filter fieldsYesNo
find-manyReturn all documents matching all filter fieldsYesNo
insertCreate a new document with the provided data fields. Auto-generates _id.NoYes
updateUpdate the first matching document with the provided data fieldsYesYes
upsertUpdate matching document or create one if not foundYesYes
deleteDelete the first matching document and return itYesNo
💡
Auto-generated _id The insert and upsert (create path) operations automatically assign a UUID to the _id field if you do not provide one in the data rules. The generated ID is included in the result and available in templates as {{.Collection.myKey._id}}.

Field Mapping Rules

Field Mapping Rules tell go-virtual where to read the value for each collection field. Two sets of rules exist per mapping:

  • Filter Rules — used for find/update/upsert/delete to match documents
  • Data Rules — used for insert/update/upsert to set document fields

Each rule has three parts: Target Field (the collection field name), Source Type (where the value comes from), and Source Key (the specific key or literal within that source).

Source TypeSource Key exampleDescription
pathidURL path parameter
querystatusQuery string parameter
headerX-User-IdHTTP request header

Output Key & Status Field

Each mapping has an Output Key — an alphanumeric identifier that names the result. Results are accessible in templates and conditions as .Collection.<outputKey>.

Every result — whether successful, empty, or failed — automatically includes a _status field:

_status: "success"
_status: "not_found"
_status: "error"
StatusWhen it occursAdditional field
"success"The operation completed and found/created/updated a documentAll document fields
"not_found"find-one/update/delete returned no match— (none)
"error"Internal execution error_error: error message string

For find-many, the result is a slice. Each element in the slice gets its own _status: "success". An empty collection returns an empty slice (not not_found).

💡
The output key is always set Even when a document is not found, .Collection.user resolves to {"_status": "not_found"} rather than nil. This means templates never panic on {{.Collection.user._status}} — it always has a value.

Using Results in Templates

Once a mapping runs, its output is available in response body and header templates under .Collection.<outputKey>:

// Mapping outputKey = "user", find-one result:
{
  "id":    "{{.Collection.user._id}}",
  "email": "{{.Collection.user.email}}",
  "name":  "{{.Collection.user.name}}",
  "found": "{{.Collection.user._status}}"
}

Conditional output based on status

{{if eq .Collection.user._status "success"}}
{
  "id":    "{{.Collection.user._id}}",
  "email": "{{.Collection.user.email}}"
}
{{else}}
{ "error": "user not found" }
{{end}}

Iterating over find-many results

// Mapping outputKey = "items", find-many result (e.g. all products in a cart)
{
  "items": [
    {{range $i, $item := .Collection.items}}
    {{if $i}},{{end}}
    {
      "id":    "{{$item._id}}",
      "name":  "{{$item.name}}",
      "qty":   {{$item.qty}}
    }
    {{end}}
  ],
  "total": {{len .Collection.items}}
}

Serializing the full result

// Dump the entire result document as compact JSON
{ "user": {{toJSON .Collection.user}} }

Using Results in Conditions

Collection output from spec-level and operation-level mappings is available in response config conditions. This lets you choose which response config to serve based on what was found (or not found) in the collection.

Use source: "collection" with a key of the form outputKey.fieldPath:

{
  "source": "collection",
  "key": "user._status",
  "operator": "eq",
  "value": "success"
}
What you want to checksourcekey
User was foundcollectionuser._status = success
User was not foundcollectionuser._status = not_found
User's role is "admin"collectionuser.role = admin
User's status is "active"collectionuser.status = active
Order total is over 100collectionorder.total > 100
⚠️
Response-scope mappings cannot influence conditions Only spec-scope and operation-scope mapping output is available for condition evaluation, because response-scope mappings run after response matching. Use spec/operation-scope mappings when the result needs to influence which response is selected.

Response-level Collection Mappings

Inside any response config editor, the Collection Mappings tab lets you add mappings that run only when this specific response is matched. These are batched with the response config — they are saved and enabled when you save the response.

End-to-End Examples

Example 1: Stateful User API

Create a mock that actually stores and retrieves users across requests. Each client gets their own isolated user table.

POST /users — Create a user

Add a response-level mapping on the "201 Created" response config:

  • Collection: users, Operation: insert, Output Key: created
  • Data Rules: email ← body:user.email, name ← body:user.name, status ← literal:active
// Response body template:
{
  "id":     "{{.Collection.created._id}}",
  "email": "{{.Collection.created.email}}",
  "name":  "{{.Collection.created.name}}"
}

GET /users/{id} — Return 200 if found, 404 if not

Add an operation-level mapping:

  • Collection: users, Operation: find-one, Output Key: user
  • Filter Rules: _id ← path:id

Create two response configs:

  • Priority 0, condition: source=collection, key=user._status, op=eq, value=success, status 200
  • Priority 10, no condition (always matches), status 404
// 200 response body:
{
  "id":     "{{.Collection.user._id}}",
  "email": "{{.Collection.user.email}}",
  "status": "{{.Collection.user.status}}"
}

Example 2: Shopping Cart

Maintain a per-client cart using find-many and insert.

Operation-level on GET /cart

  • Collection: cart_items, Operation: find-many, Output Key: items
  • No filter rules (returns all items in the collection)
{
  "items": [
    {{range $i, $item := .Collection.items}}
    {{if $i}},{{end}}
    { "sku": "{{$item.sku}}", "qty": {{$item.qty}}, "price": {{$item.price}} }
    {{end}}
  ],
  "count": {{len .Collection.items}}
}

Response-level on POST /cart/items "201 Created"

  • Collection: cart_items, Operation: insert, Output Key: added
  • Data Rules: sku ← body:sku, qty ← body:qty, price ← body:price
{ "itemId": "{{.Collection.added._id}}", "message": "added to cart" }
