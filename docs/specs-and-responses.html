Managing Specifications

go-virtual manages multiple OpenAPI 3 specs simultaneously. Each spec is independently enabled/disabled and its operations are mounted at the server's root path (or a configured base path).

Uploading a spec

Specs can be uploaded as YAML or JSON via the REST API or the Admin UI:

# Upload YAML spec
curl -X POST http://localhost:8080/_api/specs \
  -H "Content-Type: application/json" \
  -d '{
    "name": "My API",
    "content": "openapi: \"3.0.0\"\ninfo:\n  title: My API\n  version: 1.0.0\npaths: ..."
  }'

# Response
{
  "id": "spec_abc123",
  "name": "My API",
  "enabled": true,
  "operationCount": 12,
  "createdAt": "2024-01-15T10:00:00Z"
}

Spec fields

FieldTypeDescription
namestringHuman-readable name displayed in the UI
contentstringRaw YAML or JSON OpenAPI 3 content
basePathstringOptional path prefix for all operations (e.g., /v1)
enabledboolWhether this spec's operations are active
tracingboolWhether requests to this spec are traced
useExampleFallbackboolWhether standard mode can fall back to OpenAPI examples/default responses
modestringExecution mode: standard, ai, or proxy
backendUristringUpstream backend URL used by proxy fallback

Enable / disable a spec

# Disable — all operations stop responding
curl -X PUT http://localhost:8080/_api/specs/spec_abc123/disable

# Re-enable
curl -X PUT http://localhost:8080/_api/specs/spec_abc123/enable

Update a spec

You can push an updated YAML/JSON content to refresh all operations automatically:

curl -X PUT http://localhost:8080/_api/specs/spec_abc123 \
  -H "Content-Type: application/json" \
  -d '{"name": "My API v2", "content": "..."}'
⚠️
Path conflicts If two enabled specs define the same path and method, the first-registered spec wins. Disable conflicting specs or use basePath to namespace them.

Operations

When a spec is uploaded, go-virtual parses it and creates an operation record for each path+method combination. Operations are referenced when creating response configurations and script bindings.

Listing operations

curl http://localhost:8080/_api/specs/spec_abc123/operations

# Example response item
{
  "id": "op_xyz",
  "specId": "spec_abc123",
  "operationId": "getPet",
  "method": "GET",
  "path": "/pets/{id}",
  "summary": "Get a pet by ID",
  "tags": ["pets"],
  "responseCount": 2
}

Operation fields

FieldDescription
idInternal operation identifier used in API calls
operationIdThe operationId from the OpenAPI spec
methodHTTP method (GET, POST, PUT, DELETE, PATCH, etc.)
pathURL path template (e.g., /pets/{id})
tagsTags from the spec for filtering
responseCountNumber of response configs attached

Response Configurations

A response configuration defines what go-virtual returns when an operation is called. You can attach multiple response configs to a single operation — they're evaluated in priority order, and the first one whose conditions match is used.

Creating a response

curl -X POST http://localhost:8080/_api/operations/op_xyz/responses \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Success Response",
    "priority": 0,
    "statusCode": 200,
    "headers": {
      "Content-Type": "application/json",
      "X-Request-Id": "{{random.uuid}}"
    },
    "body": "{\"id\": \"{{path.id}}\", \"name\": \"{{faker.animal.name}}\"}",
    "delay": 50,
    "tag": "default"
  }'

Response configuration fields

FieldTypeRequiredDescription
namestringYesHuman-readable label for the response
priorityintegerYesEvaluation order — lower numbers run first (0, 1, 2…)
statusCodeintegerYesHTTP status code to return (200, 404, 500, etc.)
headersobjectNoHTTP headers to include in the response. Values support templates.
bodystringNoResponse body string. Supports template variables.
conditionsarrayNoArray of condition objects. If empty, this config always matches.
delayintegerNoAdditional delay in milliseconds before responding
tagstringNoTag used to organize and filter responses in the UI
💡
No conditions = always matches A response config with no conditions array (or an empty one) acts as a catch-all. Place it at a higher priority number so more specific responses run first.

Updating and deleting

# Update response body
curl -X PUT http://localhost:8080/_api/responses/resp_id \
  -H "Content-Type: application/json" \
  -d '{"statusCode": 200, "body": "{\"updated\": true}"}'

# Delete
curl -X DELETE http://localhost:8080/_api/responses/resp_id

Priority & Matching Order

When a request arrives for an operation, go-virtual evaluates all attached response configs in ascending priority order (lowest number first). The first config whose conditions all pass is selected.

Example scenario

# Priority 0 — Return 401 if Authorization header is missing
{
  "priority": 0, "statusCode": 401,
  "conditions": [{"source": "header", "key": "Authorization", "operator": "notExists"}]
}

# Priority 1 — Return 404 for specific IDs
{
  "priority": 1, "statusCode": 404,
  "conditions": [{"source": "path", "key": "id", "operator": "eq", "value": "0"}]
}

# Priority 2 — Default success response (no conditions)
{
  "priority": 2, "statusCode": 200,
  "body": "{\"id\": \"{{path.id}}\", \"name\": \"{{faker.name.first}}\"}"
}

Reordering via the API

curl -X PUT http://localhost:8080/_api/responses/resp_id/priority \
  -H "Content-Type: application/json" \
  -d '{"priority": 5}'
💡
Admin UI drag-and-drop In the Response Designer, you can drag response cards to reorder them visually. Priority numbers are automatically recalculated.

Response Delays

Simulate realistic network latency by setting delay on a response config. The server waits the specified number of milliseconds before sending the response.

{
  "name": "Slow endpoint",
  "statusCode": 200,
  "delay": 2000,  // 2 second delay
  "body": "{\"result\": \"slow\"}"
}

Use delays to test:

  • Frontend loading states and skeleton screens
  • Client timeout handling
  • Perceived performance of different API designs

Spec Modes

Each spec runs in one mode. In every case, saved responses are evaluated first; only after they miss does the selected fallback run.

ModeFallback behavior after saved responses miss
standardUse the OpenAPI example/default fallback when enabled
aiGenerate a structured response from the request and response schema, then record it
proxyForward to the configured backend, then record the upstream response

Use the spec mode selector in the UI or the explicit mode API to switch between behaviors:

curl -X PUT http://localhost:8080/_api/specs/spec_abc123/mode \
  -H "Content-Type: application/json" \
  -d '{"mode": "proxy"}'

curl -X PUT http://localhost:8080/_api/specs/spec_abc123/backend \
  -H "Content-Type: application/json" \
  -d '{"backendUri": "https://api.example.com"}'

curl -X POST http://localhost:8080/_api/specs \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Live API",
    "content": "...",
    "backendUri": "https://api.example.com"
  }'

When a spec runs in proxy mode and an operation has no matching saved response config, the request is forwarded to the configured backendUri and the real response is returned.

mTLS for backend requests

If your backend requires mutual TLS authentication, configure client certificates in config.yaml:

proxy:
  mtls:
    certFile: /etc/certs/client.crt
    keyFile: /etc/certs/client.key
    caCertFile: /etc/certs/ca.crt

See Configuration — Proxy for all proxy options.

Generated & Recorded Responses

AI mode and proxy mode both produce replayable response configs. These responses are stored on the operation and shown on a dedicated generated responses page in the UI, separate from manual responses.

  • AI origin — generated at runtime and saved for replay
  • Proxy origin — captured from the upstream backend and saved for replay
  • Manual origin — created directly by a user

Recorded/generated responses normally use a signature condition. That lets the runtime match the exact request fingerprint again later without re-running AI or proxy fallback.

⚠️
Sensitive data Recorded responses may contain real user data. Review and sanitize recorded mocks before committing them to version control or sharing them.

Complete Examples

REST CRUD mock — User resource

# POST /users — 201 Created
{
  "name": "Create User", "priority": 0, "statusCode": 201,
  "headers": {"Location": "/users/{{random.uuid}}"},
  "body": "{\"id\": \"{{random.uuid}}\", \"email\": \"{{body.email}}\", \"createdAt\": \"{{timestamp.iso}}\"}"
}

# GET /users/{id} — 404 when id starts with "invalid"
{
  "name": "Not Found", "priority": 0, "statusCode": 404,
  "conditions": [{"source": "path", "key": "id", "operator": "startsWith", "value": "invalid"}],
  "body": "{\"error\": \"User not found\", \"id\": \"{{path.id}}\"}"
}

# GET /users/{id} — 200 default
{
  "name": "Success", "priority": 10, "statusCode": 200,
  "body": "{\"id\": \"{{path.id}}\", \"name\": \"{{faker.name.first}} {{faker.name.last}}\", \"email\": \"{{faker.internet.email}}\"}"
}

Simulating a flaky API (random 500s)

# Trigger 500 when query param ?fail=true
{
  "name": "Server Error", "priority": 0, "statusCode": 500,
  "conditions": [{"source": "query", "key": "fail", "operator": "eq", "value": "true"}],
  "body": "{\"error\": \"Internal server error\"}",
  "delay": 3000
}

Authentication-aware mock

# 401 when no Authorization header
{
  "name": "Unauthorized", "priority": 0, "statusCode": 401,
  "conditions": [{"source": "header", "key": "Authorization", "operator": "notExists"}],
  "body": "{\"error\": \"Missing Authorization header\"}"
}

# 403 when token doesn't start with "Bearer "
{
  "name": "Forbidden", "priority": 1, "statusCode": 403,
  "conditions": [{"source": "header", "key": "Authorization", "operator": "notStartsWith", "value": "Bearer "}],
  "body": "{\"error\": \"Invalid token format\"}"
}

# 200 success (catch-all)
{
  "name": "Success", "priority": 10, "statusCode": 200,
  "body": "{\"data\": \"{{faker.lorem.sentence}}\"}"
}
