Admin UI Guide

go-virtual ships with a full-featured web interface at /_ui/. This guide walks through every page — what it shows, how to interact with it, and what you can accomplish without writing a single API call.

Opening the UI

Start the server and navigate to http://localhost:8080/_ui/ in any modern browser. The UI works on Chrome, Firefox, Safari, and Edge.

go-virtual serve
# Admin UI at http://localhost:8080/_ui/
💡
Headless mode disables the UI and admin API Running with --headless disables both the Admin UI and the Admin API. Use this flag when you only want the request-serving runtime.

  • Top Operations by Request Volume — Horizontal bar chart of the six busiest operations.
  • Response-Time Breakdown — Bar chart of min / avg / max latency for the top eight operations.

Server Status panel

Shows uptime, start time, requests/sec, and total errors. A color-coded progress bar turns yellow above 5% error rate and red above 20%.

Recent Errors panel

A scrollable log of the latest error responses. Each entry shows the HTTP method badge, path (monospace), status code, timestamp, and a snippet of the error message. Empty when all is healthy.

Operation Statistics table

A sortable table with one row per operation: method, path, request count, error count (red when non-zero), average / min / max response time, and last-hit timestamp. Click any column header to sort.

💡
Prometheus link The Dashboard header includes a "Prometheus Metrics" link that opens /_prometheus directly — handy for quickly checking the raw Prometheus output.

  • Specification File — Drag-and-drop area or click to browse. Accepts .yaml, .yml, .json. Dropping a file auto-fills Name and Description from the spec's info block.
  • Paste Content — Alternatively paste raw YAML or JSON. Mutually exclusive with file upload.

Spec cards

After upload, each spec appears as a card. The right side of every card has four action buttons:

ButtonEffect
Example Fallback toggle (amber)When enabled, operations with no matching response config fall back to the OpenAPI spec's built-in example values instead of returning a 404.
Tracing toggle (yellow)Enable or disable trace capture for all operations in this spec.
Enable / Disable toggle (green)Enable or disable all operations in the spec. Disabled specs are completely inactive.
Delete (trash)Permanently removes the spec and all its response configs.

Click the spec name to navigate to the Spec Detail page.

Spec Detail & Operations

The Spec Detail page shows all operations in the spec, grouped by tag. It also lets you select the spec mode, configure a backend for proxy fallback, and control which tags are enabled.

Operations list

Operations are grouped under expandable tag sections. Each row shows:

Click any row to open the Operation Detail page for that operation.

  • An amber sparkles icon (✨) on an operation row means the OpenAPI spec has example values for that operation, and the "Example Fallback" feature can use them.
  • The response count badge shows how many mock response configs are attached.

Response Configuration

The Operation Detail page is where you build mock response configs. Click Add Response to open the Response Config Editor.

Response cards

Each response config appears as an expandable card on the operation detail page. Collapsed view shows:

  • A drag handle icon on the left (visual; re-ordering is done via the priority field or Edit)
  • A priority badge (circle with number — lower numbers evaluate first)
  • Response name, tag badge, status code badge (green for 2xx, red for 4xx/5xx)
  • Number of conditions
  • Enable / Edit / Delete buttons on the right

Click the chevron or anywhere on the card to expand it and see conditions, headers, and the response body preview.

💡
Script output variables If a script is bound to the operation, its output fields are accessible as {{.script.<outputKey>.fieldName}}. These appear in the template panel once a binding exists. See Script Bindings below.

Signature Configuration

Each operation has an optional Signature configuration that controls what parts of the request are hashed to produce a deterministic identifier. This lets you create response configs that match only specific combinations of request parameters.

On the Operation Detail page, scroll to the Signature Configuration section and click Configure.

Configure panel

Path Parameters

Click All to include every path param, or toggle individual path parameters on/off using the chip buttons (violet = included, white = excluded).

All id version format

Query Parameters

Click Include All to track all query params, or type individual parameter names into the input and press Add. Added params appear as chips with an ✕ to remove.

Headers

Add specific header names to include in the signature (e.g., X-Tenant-Id). Leave empty to include no headers.

Request Body

A checkbox enables body inclusion in the signature. When ticked, an additional input section lets you add JSONPath selectors (e.g., user.id, items.0.sku) to hash only specific fields instead of the whole body.

Click Save to apply or Reset to defaults to clear the configuration.

Each panel shows the list of mappings for that scope. Each row displays the execution order, name, collection operation, collection name, and output key. You can toggle enabled/disabled, reorder, edit, or delete individual mappings.

Add Mapping form

Click + Add Mapping to open the form. Fill in:

  • Name — a human-readable label
  • Collection Name — the collection inside the session to operate on
  • Operation — find-one, find-many, insert, update, upsert, or delete
  • Output Key — the name used in templates ({{.Collection.<outputKey>}}) and conditions (source=collection, key=<outputKey>.field)
  • Filter Rules — for find/update/upsert/delete: which fields to match on, and where to read the values
  • Data Rules — for insert/update/upsert: which fields to write, and where to read the values
  • Execution Order — lower numbers run first

See Collection Mappings for full details on operations, field source types, and the _status field.

Validation Rules

Validation Rules evaluate flexible condition trees against incoming requests and attach named properties to the pass or fail outcome. They appear on the Spec Detail and Operation Detail pages.

Where to find them

LocationScopeWhen they run
Spec Detail pageSpec-levelEvery request to any operation in the spec
Operation Detail pageOperation-levelEvery request to that specific operation

Validation Rules panel

Each panel shows rules in execution order. Each row displays the name, a preview of the pass properties, and a preview of the fail properties. You can toggle, reorder, edit, and delete rules.

⇅
1
isAdmin
pass → userRole=admin fail → userRole=guest

Add/Edit Rule form

Click + Add Rule to open the rule editor. Fill in:

  • Name — used as the key in templates ({{.Validation.<name>._status}}) and conditions (source=validation, key=<name>.field)
  • Condition Tree — build a nested AND/OR/NOT tree of request conditions using the visual editor
  • On Pass Properties — key-value pairs attached to the result when the tree evaluates to true
  • On Fail Properties — key-value pairs attached to the result when the tree evaluates to false
  • Execution Order — lower numbers run first (spec-level rules run before operation-level)

See Validation Rules for full details on condition trees, pass/fail properties, and example patterns.

Trace Viewer

The Traces page provides a split-panel view: a scrollable trace list on the left and a detail panel on the right.

Live vs History mode

  • Live mode (default) — A WebSocket connection streams new traces in real time as requests arrive. The button shows a pulsing green Activity icon and the label "Live". New traces appear at the top of the list (newest first). Up to 100 traces are kept in the in-page buffer.
  • History mode — Click the Live button to pause. The list freezes. Use the Refresh button to reload from the server, or click Go Live to resume streaming.

Filters

  • Search box — Type to filter traces by path, HTTP method, or spec name. The filter applies instantly to both the list and the live stream.
  • Spec dropdown — Show traces from only one spec.

Add / Edit Entry modal

Click Add Entry or the pencil button. A Monaco JSON editor allows you to write any string value — JSON objects, arrays, or plain strings. Validation feedback appears if the JSON is malformed.

⚠️
Danger Zone — Clear All At the bottom of the Store page is an expandable "Danger Zone" section with a Clear All button (red). This removes every key from the global store. A confirmation modal warns that active sessions will retain their current snapshots until they expire.

Sessions

The Sessions page shows all active sessions — clients that have sent requests with an X-Virtual-Session-Id header. The page has a dark teal aesthetic.

Session Detail panel

Click any row to open a right-side detail panel (width: 320px). It shows:

  • Full session ID (monospace, teal)
  • Created and Last Active timestamps (full ISO format)
  • Entry count
  • Store Snapshot — all key-value pairs in this session's store, formatted as JSON
  • Store Access Events (if tracing has captured them) — a list of get/set/has/delete/keys operations with keys and relative timestamps

Invalidate All

The red Invalidate All button (top right, visible when sessions exist) shows a confirmation modal before wiping all sessions. A Refresh button reloads the session list.

💡
Sessions expire automatically You don't need to manually invalidate sessions. They are automatically cleaned up after the configured inactivity timeout (default: 30 minutes). Use the Sessions page mainly to debug stateful script behavior or force-reset a specific client's session.

Tags

Tags are labels you attach to response configurations to group them. The Spec Detail page lets you enable or disable whole groups of responses at once by toggling tags.

Tag Manager page

The Tags page lists all tags. Click Create Tag to add a new one:

Name *
v2
Description
Responses for API version 2 clients
  • The default tag always exists and cannot be edited or deleted. Response configs with no tag are assigned to default automatically.
  • Custom tags can be edited (pencil) or deleted (trash). Deleting a tag removes it from all response configs that referenced it — those configs fall back to the default tag.

Using tags on spec detail

Once you have custom tags, go to any Spec Detail page and find the Enabled Tags section. Toggle tags on/off to instantly include or exclude entire groups of response configs from the matching pipeline — no editing of individual responses needed.

💡
Tag use case: A/B testing and feature rollouts Create a feature-x tag. Add response configs with new behavior and tag them feature-x. When you want to activate the feature, enable the tag on the spec. When you want to roll back, disable it — no code changes required.
