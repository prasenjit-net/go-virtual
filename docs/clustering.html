go-virtual / Clustering

Clustering & Horizontal Scaling

Run multiple go-virtual instances behind a load balancer. Two patterns are supported: a read-only / headless pattern using file storage (simple, no MongoDB required) and a live-sync pattern using MongoDB with change streams or polling (supports runtime admin mutations).

Pattern 1: Read-Only Headless

If your specs and responses are configured once and do not change during the lifetime of a deployment, you do not need MongoDB or any cross-instance synchronisation. Every instance starts with the same data and serves requests identically — there are no writes to propagate.

How it works

In headless mode (server.headless: true) the entire admin API (/_api/) and admin UI (/_ui/) are not registered — not just protected, but completely absent from the router. The only routes mounted are /_prometheus and the catch-all proxy handler. This means:

  • No mutation can reach the storage layer at runtime — the route table and global store cache are built once at startup and never change.
  • Any number of instances reading the same data directory (or image layer) will always agree on routes.
  • No sync mechanism, no change stream, no polling is needed.

Workflow

  1. Author — configure specs, responses, scripts, and global store values using the Admin UI on a local or admin-only instance (non-headless).
  2. Export — copy the data/ directory (or export an archive) into your container image or deployment artifact.
  3. Deploy — start N replicas with server.headless: true pointing at the baked-in data directory. Each instance is identical and stateless with respect to mock data.
  4. Update — when specs change, repeat from step 1 and roll out a new image/deployment.
server:
  port: 8080
  host: "0.0.0.0"
  headless: true         # disables /_api/ and /_ui/ entirely

storage:
  type: "file"
  path: "/app/data"       # read-only at runtime; baked into the image

# Redis sessions — required only if your tests use X-Virtual-Session-Id
session:
  storeType: "redis"
  redis:
    addr: "redis:6379"
💡
Keep one non-headless admin instance separate Run a single non-headless instance (not behind the load balancer) for authoring and exporting. It never receives production traffic and is the only place mutations happen.

Pattern 2: MongoDB Live Sync

Use this pattern when specs and responses need to be updated at runtime — by multiple teams, via the Admin UI, or through automated pipelines — and all instances must reflect changes immediately without a redeploy.

The default file and memory storage backends are single-instance only. When you need:

  • High availability — survive instance crashes without downtime
  • Load distribution — spread mock traffic across multiple pods/containers
  • Shared admin operations — upload a spec once and have it visible on all instances immediately

… you need MongoDB storage with cross-instance synchronisation enabled.

The synchronisation problem

go-virtual keeps two critical in-memory caches that make it fast:

  1. Route table (proxy.Engine.routes) — built from MongoDB at startup and used for every request to determine which spec/operation a request belongs to. Without synchronisation, uploading a spec to Instance A leaves Instance B serving 404 Not Found for the new routes until it restarts.
  2. Global store cache (MongoGlobalStore.cache) — an in-memory write-through map. Scripts that call store.get() read from this map. Without synchronisation, a value written by a script running on Instance A is invisible to scripts running on Instance B until the next startup.

The sync subsystem solves both problems by watching MongoDB for external writes and propagating changes to every instance in real time.

Architecture

All instances connect to the same MongoDB database. Admin API mutations (spec upload, response creation, store writes) persist directly to MongoDB. Each instance independently watches MongoDB for changes and updates its local caches.

                Load Balancer
               ┌──────┴───────┐
          Instance A       Instance B
          ┌──────────┐     ┌──────────┐
          │ routes   │     │ routes   │ ← both reload on change
          │ cache    │     │ cache    │ ← both patch on write
          └────┬─────┘     └────┬─────┘
               │                │
               └───────┬────────┘
                       │ shared
                  ┌────▼──────────────────┐
                  │      MongoDB          │
                  │ ┌───────────────────┐ │
                  │ │ gv_specs          │ │ ── Change Stream ──► all instances
                  │ │ gv_operations     │ │ ── Change Stream ──► all instances
                  │ │ gv_global_store   │ │ ── Change Stream ──► all instances
                  │ └───────────────────┘ │
                  └───────────────────────┘

Event flow when a spec is uploaded

  1. Client calls POST /_api/specs on Instance A.
  2. Instance A writes the spec document to gv_specs and all operation documents to gv_operations in MongoDB.
  3. Instance A immediately calls engine.ReloadRoutes() on its own engine.
  4. MongoDB emits insert change events on both collections.
  5. Instance B's change stream goroutines receive the events and trigger a debounced route reload (200 ms quiet period).
  6. Within ~200 ms of the write, all instances serve the new routes.
💡
Debounce prevents burst reloads Uploading a spec with 50 operations generates 51 MongoDB write events (1 spec + 50 operations). The 200 ms debounce window collapses these into a single ReloadRoutes() call per instance.

Prerequisites

MongoDB replica set (recommended)

MongoDB change streams — the lowest-latency sync mechanism — require a replica set or a sharded cluster. A standalone mongod process does not support them.

Deployment typeChange streamsNotes
MongoDB Atlas (any tier)✅ YesReplica set by default
Replica set (self-hosted)✅ YesOne primary, one or more secondaries
Sharded cluster✅ YesConnect to mongos
Standalone mongod❌ NoUse mode: polling or add --replSet rs0
Standalone with --replSet rs0 + rs.initiate()✅ YesSingle-node replica set, common in dev/CI

Starting a single-node replica set (dev / CI)

# Start mongod with replica set name
mongod --replSet rs0 --port 27017 --dbpath /data/db

# In a mongo shell, initialise the set (once only)
mongosh --eval "rs.initiate()"

Or use the Docker image:

docker run -d --name mongo \
  -p 27017:27017 \
  mongo:7 \
  mongod --replSet rs0 --bind_ip_all

# Initialise once
docker exec mongo mongosh --eval "rs.initiate()"

Using polling mode (no replica set)

If you cannot configure a replica set, use mode: polling. Propagation will lag by up to pollIntervalSeconds (default 10 s), but no MongoDB configuration changes are needed.

Sync Mechanism

Change streams

When mode is "change_stream" or "auto" on a replica set, go-virtual opens a long-lived change stream cursor on each watched collection using a dedicated MongoDB connection (separate from the storage connection pool). A goroutine per collection decodes incoming events and dispatches them:

  • gv_specs / gv_operations → signals the route reload channel
  • gv_global_store → patches the in-memory store cache (re-reads the document for insert/update; removes the key for delete)

The route reload channel is consumed by a debounce goroutine that waits for a 200 ms quiet period before calling engine.ReloadRoutes(). This collapses rapid burst events (e.g. bulk spec upload) into a single reload.

Transient cursor errors (network blip, cursor expiry) are retried with exponential back-off (1 s → 2 s → 4 s → … up to 60 s).

Polling

When mode is "polling" or as the fallback in "auto" mode on a standalone deployment, go-virtual runs a periodic scan every pollIntervalSeconds seconds. Each document is fingerprinted with SHA-256 of its data payload. Documents whose fingerprints have changed since the last scan are dispatched as synthetic change events using the same handler path as change streams.

The initial scan at startup records fingerprints without emitting events, preventing a flood of false-positive reloads on boot.

What is watched

gv_specsinsert, replace, update, deleteDebounced route table reload
gv_operationsinsert, replace, update, deleteDebounced route table reload
gv_global_storeinsert, replace, update, deleteIn-memory store cache patch

Configuration

Minimal clustered config

storage:
  type: "mongo"
  mongo:
    uri: "mongodb://mongo:27017/?replicaSet=rs0"
    database: "go-virtual"
    sync:
      mode: "auto"

Full clustered config with all options

server:
  port: 8080
  host: "0.0.0.0"

storage:
  type: "mongo"
  mongo:
    uri: "mongodb://mongo:27017/?replicaSet=rs0"
    database: "go-virtual"
    collectionPrefix: "gv_"
    connectTimeoutSeconds: 10
    # Time budget for retrying the initial ping until the replica set is ready.
    # Prevents startup failures in Docker Swarm / Kubernetes where rs.initiate()
    # may complete after this container starts.
    startupRetrySeconds: 90
    sync:
      mode: "auto"          # auto | change_stream | polling | off
      pollIntervalSeconds: 10

# Required for shared session state across instances
session:
  storeType: "redis"
  headerName: "X-Virtual-Session-Id"
  redis:
    addr: "redis:6379"
    keyPrefix: "go-virtual:sessions"

logging:
  level: "info"
  format: "json"

Session State

go-virtual sessions (per-client script state seeded from the global store) are not stored in MongoDB. The two supported session backends are:

Session backendMulti-instanceNotes
memory (default)❌ NoSessions are per-instance. A client routed to a different instance sees no session state.
redis✅ YesSessions are stored in Redis and shared across all instances.
⚠️
Use Redis sessions in clustered deployments If your application under test uses the session header (X-Virtual-Session-Id) to maintain state across requests, you must configure session.storeType: redis. Without it, sessions are silently lost whenever a request lands on a different instance. 
session:
  storeType: "redis"
  headerName: "X-Virtual-Session-Id"
  inactivityTimeout: "30m"
  maxSessions: 10000
  redis:
    addr: "redis:6379"
    username: ""
    password: ""
    db: 0
    keyPrefix: "go-virtual:sessions"

Global Store Consistency

The global key-value store is backed by MongoDB (gv_global_store collection) when using MongoDB storage. All instances share the same data.

Write propagation

When a Starlark script calls store.set("key", value) on Instance A:

  1. The value is written to the in-memory cache on Instance A immediately.
  2. The write is persisted to MongoDB.
  3. MongoDB emits a change event on gv_global_store.
  4. All other instances receive the event via their change stream (or pick it up on the next poll cycle) and update their in-memory caches.

Consistency model

The global store uses last-write-wins semantics. If two instances write the same key concurrently, MongoDB determines the winner (the last write to reach the primary). The change stream delivers the winning value to all instance caches.

💡
Admin writes also sync Global store entries set via the Admin UI or admin API (PUT /_api/store/:key) are also propagated to all instances through the same change stream mechanism.

Tracing & Metrics

Traces and statistics are kept in-memory per instance and are not shared across the cluster. This is intentional — cross-instance trace aggregation would require additional infrastructure (e.g. a distributed tracing backend).

Implications for clustered deployments:

  • The Admin UI on Instance A shows only traces from Instance A. Route requests to a specific instance if you need to observe a particular request's trace.
  • Prometheus metrics (/_prometheus) are per-instance. Aggregate them with a Prometheus scrape job that targets all instances (e.g. via Kubernetes service discovery or static scrape targets).
  • The trace WebSocket stream (/_api/traces/stream) is per-instance.
💡
Headless mode for worker instances Worker instances that should not expose the Admin UI can run with server.headless: true. This disables /_ui/ and /_api/. Proxy routing and /_prometheus remain available.

Docker Compose Example

A full clustered setup with two go-virtual instances, MongoDB replica set, and Redis:

version: "3.9"

services:
  mongo:
    image: mongo:7
    command: mongod --replSet rs0 --bind_ip_all
    ports:
      - "27017:27017"
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 5s
      retries: 10

  mongo-init:
    image: mongo:7
    depends_on:
      mongo:
        condition: service_healthy
    command: mongosh --host mongo:27017 --eval "rs.initiate()"
    restart: "no"

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

  gv-1:
    image: ghcr.io/prasenjit-net/go-virtual:latest
    environment:
      GOVIRTUAL_STORAGE_TYPE: mongo
      GOVIRTUAL_STORAGE_MONGO_URI: mongodb://mongo:27017/?replicaSet=rs0
      GOVIRTUAL_STORAGE_MONGO_SYNC_MODE: auto
      GOVIRTUAL_SESSION_STORETYPE: redis
      GOVIRTUAL_SESSION_REDIS_ADDR: redis:6379
    ports:
      - "8081:8080"
    depends_on:
      - mongo-init
      - redis

  gv-2:
    image: ghcr.io/prasenjit-net/go-virtual:latest
    environment:
      GOVIRTUAL_STORAGE_TYPE: mongo
      GOVIRTUAL_STORAGE_MONGO_URI: mongodb://mongo:27017/?replicaSet=rs0
      GOVIRTUAL_STORAGE_MONGO_SYNC_MODE: auto
      GOVIRTUAL_SESSION_STORETYPE: redis
      GOVIRTUAL_SESSION_REDIS_ADDR: redis:6379
    ports:
      - "8082:8080"
    depends_on:
      - mongo-init
      - redis

  nginx:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - gv-1
      - gv-2

Minimal nginx.conf for the load balancer

events {}
http {
  upstream go_virtual {
    server gv-1:8080;
    server gv-2:8080;
  }
  server {
    listen 80;
    location / {
      proxy_pass http://go_virtual;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
    }
  }
}
