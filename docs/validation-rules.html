Validation Rules

Validation Rules let you evaluate complex conditions against incoming requests and attach named properties to pass or fail outcomes. Use them to classify requests — authenticated vs. anonymous, premium vs. free tier, valid vs. malformed — then branch your responses and templates based on the result.

How It Works

A Validation Rule is a named check that runs against every incoming request. It has a condition tree that evaluates to either pass or fail, plus a set of properties to attach to the result for each outcome. All rules for a scope run in execution order, and their named results flow into the template context and condition evaluator.

Validation Rules are the flexible alternative to hard-coded conditions on individual response configs. Instead of repeating "Authorization header exists AND has role=admin" on every response, define it once as a validation rule called isAdmin, then reference source=validation, key=isAdmin._status in any condition.

Pipeline position

Validation rules participate in a mixed-order pipeline alongside scripts and collection mappings. Within a scope, all three step types are interleaved by their order field, so you can run a collection lookup before a validation rule, or a script after one.

StepWhat happens
① RoutePath + method matched to an OpenAPI operation
② SessionSession resolved from header
③ Recorded responsesSignature-matched pre-recorded responses served immediately
④ Spec-scope pipelineScripts, validation rules, and collection mappings at spec level run in user-defined order.
⑤ Proxy checkProxy mode evaluated using spec-scope outputs
⑥ Operation-scope pipelineScripts, validation rules, and collection mappings at operation level run in user-defined order.
⑦ Response matchResponse configs evaluated — can use validation results in conditions
⑧ Template renderResponse body + headers rendered — can use validation results in templates
⚠️
A failing validation aborts the remaining scope steps If a validation rule's condition tree evaluates to fail, all remaining steps in that scope (later scripts, validations, and collection mappings) are skipped. Design your rule order accordingly — place gates early if you want them to short-circuit expensive lookups that follow.

Scopes: Spec & Operation

Validation Rules exist at two scopes:

📄
Spec Level
Runs for every request to any operation in this spec. Use for cross-cutting checks like authentication, tenant identification, or feature flags that apply to the whole API.
🔗
Operation Level
Runs only for requests that match a specific operation. Use for operation-specific validation like "is this a valid order ID" or "does the user own this resource."

Spec-level rules run first, then operation-level rules. All results accumulate in the same named map — a spec-level rule named auth and an operation-level rule named auth would overwrite each other. Use distinct names to avoid conflicts.

Condition Trees

Each validation rule has a condition tree — a flexible nested structure of AND, OR, and NOT logic applied to request conditions. This is more expressive than the flat AND-only array used by response configs.

Tree structure

A tree node is either:

  • A leaf — a single condition (source, key, operator, value)
  • A logical node — an operator (AND, OR, NOT) with child nodes
// AND: Authorization header exists AND role equals admin
{
  "operator": "AND",
  "children": [
    {
      "condition": {
        "source": "header", "key": "Authorization",
        "operator": "exists"
      }
    },
    {
      "condition": {
        "source": "body", "key": "user.role",
        "operator": "eq", "value": "admin"
      }
    }
  ]
}

UI condition builder

In the Admin UI, the condition tree is built visually using a drag-and-drop tree editor. You can add conditions, wrap groups in AND/OR, and toggle individual conditions without writing JSON manually.

Validation Rule: isAdmin
AND
header Authorization exists
OR
body user.role eq "admin"
header X-Admin-Token exists

On Pass / On Fail Properties

Each validation rule can attach key-value properties to the result depending on whether the condition tree passes or fails. These properties are merged into the named result and accessible in templates and conditions.

FieldDescription
On Pass (onSuccess)Properties to attach when the condition tree evaluates to true
On Fail (onFailure)Properties to attach when the condition tree evaluates to false

Both are optional plain string-to-string maps. Example:

Rule: authCheck
On Pass
userRoleadmin tierpremium
On Fail
userRoleguest reasonunauthorized

With this setup, {{.Validation.authCheck.userRole}} is always safe to use in a template — it resolves to "admin" on pass or "guest" on fail.

Output & Status Field

The result of each rule is accessible under .Validation.<ruleName>. It always includes a _status field:

FieldValueWhen
_status"pass"Condition tree evaluated to true
_status"fail"Condition tree evaluated to false
On Pass propertiesYour configured valuesOnly when _status = "pass"
On Fail propertiesYour configured valuesOnly when _status = "fail"
 
// Rule "authCheck" passes: condition tree is true
.Validation.authCheck = {
  "_status": "pass",
  "userRole": "admin",
  "tier": "premium"
}

// Rule "authCheck" fails: condition tree is false
.Validation.authCheck = {
  "_status": "fail",
  "userRole": "guest",
  "reason": "unauthorized"
}

Rules with no On Pass / On Fail properties still produce a _status field, so {{.Validation.myRule._status}} is always safe to reference.

Using Results in Templates

Access validation results in response body and header templates using .Validation.<ruleName>.<field>:

// Embed the user role from the authCheck rule:
{
  "role":    "{{.Validation.authCheck.userRole}}",
  "status": "{{.Validation.authCheck._status}}"
}

Conditional rendering based on pass/fail

{{if eq .Validation.authCheck._status "pass"}}
{
  "message": "Welcome, {{.Validation.authCheck.userRole}}",
  "data": { ... }
}
{{else}}
{
  "error": "Access denied: {{.Validation.authCheck.reason}}"
}
{{end}}

Use validation properties in response headers

You can also use validation results in response headers. For example, set a header based on the resolved role:

// Header value (key: X-User-Role):
{{.Validation.authCheck.userRole}}

Using Results in Conditions

Validation results are available as a condition source for response config selection. Use source: "validation" with a key of the form ruleName.fieldPath:

{
  "source": "validation",
  "key": "authCheck._status",
  "operator": "eq",
  "value": "pass"
}
What you want to checksourcekey
Auth check passedvalidationauthCheck._status = pass
Auth check failedvalidationauthCheck._status = fail
Resolved role is "admin"validationauthCheck.userRole = admin
Tier is "premium"validationauthCheck.tier = premium
💡
Combine validation and collection sources A single response config can use both source=validation and source=collection conditions together. For example: match only when the user is authenticated (validation) AND their account exists in the users collection (collection).

Operation-level Validation Rules

Open any operation from the spec detail. The Validation Rules panel appears below the Script Bindings section on the Operation Detail page. It works identically to the spec-level panel but scoped to this operation only.

Trace viewer

Validation rule results appear in the Traces page under each trace's detail panel. The Validations section shows each rule that ran: name, scope (spec/operation), pass/fail status, properties, and execution duration.

End-to-End Examples

Example 1: Authentication gate

Create a spec-level validation rule to check authentication, then use it to serve different responses.

Step 1: Create the validation rule at spec level:

  • Name: auth
  • Condition: header Authorization exists
  • On Pass: status=authenticated
  • On Fail: status=anonymous

Step 2: Create response configs for GET /profile:

  • Priority 0 — condition: source=validation, key=auth._status, op=eq, value=pass → 200 OK
  • Priority 10 — no conditions → 401 Unauthorized
// 200 response body:
{
  "message": "Authenticated user",
  "status": "{{.Validation.auth.status}}"
}

// 401 response body:
{
  "error": "Unauthorized",
  "hint": "Include an Authorization header"
}

Example 2: Role-based responses

Return different data depending on whether the caller is an admin or a regular user.

Spec-level rule isAdmin:

  • Condition: header X-Role eq admin
  • On Pass: role=admin, canDelete=true
  • On Fail: role=user, canDelete=false

Response configs for GET /resources:

  • Priority 0 — condition: source=validation, key=isAdmin.role, op=eq, value=admin → returns all fields including sensitive data
  • Priority 10 — no conditions → returns limited public fields
// Admin response includes canDelete from validation properties:
{
  "resources": [...],
  "permissions": {
    "canDelete": "{{.Validation.isAdmin.canDelete}}",
    "role": "{{.Validation.isAdmin.role}}"
  }
}

Example 3: Combining validation + collection

Use both features together — validate the token header, then look up the user record only if the token is present.

Spec-level validation rule hasToken: condition header X-Auth-Token exists

Operation-level collection mapping on GET /users/{id}: find-one users, filter _id ← path:id, outputKey=found

Response config conditions (priority 0 — success case):

[
  { "source": "validation", "key": "hasToken._status", "operator": "eq", "value": "pass" },
  { "source": "collection", "key": "found._status", "operator": "eq", "value": "success" }
]

This responds with 200 only when the token is present AND the user exists. Any other combination falls through to a lower-priority response returning 401 or 404.
