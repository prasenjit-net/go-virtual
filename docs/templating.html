Templating & Conditions

Use template variables to produce dynamic response bodies and headers. Match response configurations using flexible condition rules on any part of the request.

Template Syntax

Response bodies and header values are processed through go-virtual's template engine. Variables are referenced with double-curly-brace syntax:

{{ namespace.variable }}
{{ namespace.function(arg1, arg2) }}

Templates are rendered per-request, so each call gets fresh values for random/faker variables.

💡
Faker is deterministic per request Faker data is seeded from the request path and query parameters. The same URL will always produce the same fake values, making tests reproducible.

Request Variables

Echo values from the incoming request directly into your response. Two styles work — the preferred dot-notation and the legacy function style:

💡
Two styles — both work {{.Path.id}} (preferred) and {{path "id"}} (legacy) are equivalent. New templates should use the dot-notation style.
PreferredLegacyDescription
{{.Path.id}}{{path "id"}}URL path parameter
{{.Query.page}}{{query "page"}}Query string parameter
{{.Header.authorization}}{{header "authorization"}}HTTP header (key lowercased)
{{.Body.user.name}}{{body "user.name"}}JSON body field (dot path)
{{.RawBody}}{{rawBody}}Raw body string
{{.Method}}n/aHTTP method (GET, POST…)
{{.URL}}n/aFull request URL
{{.RequestID}}n/aStable UUID for this request
{{store "key"}}n/aSession store read
{{counter "hits"}}n/aIncrement and return session counter
 
{
  "id": "{{.Path.id}}",
  "page": "{{.Query.page}}",
  "user": "{{.Body.user.name}}",
  "method": "{{.Method}}",
  "requestId": "{{.RequestID}}"
}

Body dot-traversal

{{.Body.user.address.city}} traverses the parsed JSON body natively. For array access or complex paths use {{body "items.0.id"}} (gjson-style path).

Session store access

{
  "loginCount": "{{store "login_count"}}",
  "requestNumber": {{counter "req"}}
}

Script Output Variables

When a Starlark script is bound to an operation, its return value is available under {{.Script.<outputKey>.<field>}}:

// Script bound with outputKey = "pricing" returns:
{ "total": 99.99, "tax": 8.99 }

// Template:
{
  "total": {{.Script.pricing.total}},
  "tax": {{.Script.pricing.tax}},
  "formatted": "{{currency .Script.pricing.total "$"}}",
  "json": {{toJSON .Script.pricing}}
}

See Starlark Scripting for full details on creating and binding scripts.

Collection Output Variables

When a Collection Mapping runs, its result is stored under {{.Collection.<outputKey>}}. Results always include a _status field indicating whether the operation succeeded.

ExpressionDescription
{{.Collection.user._status}}Status: "success", "not_found", or "error"
{{.Collection.user._id}}The document's auto-generated or matched _id
{{.Collection.user.email}}A field named email on the document
{{.Collection.user._error}}Error message string (only when _status is "error")
{{len .Collection.items}}Number of results for a find-many mapping
{{toJSON .Collection.user}}Serialize the full result document to JSON
 
// Mapping outputKey = "user", find-one — user found:
{
  "id":     "{{.Collection.user._id}}",
  "email": "{{.Collection.user.email}}",
  "status": "{{.Collection.user._status}}"
}

// Iterate find-many results (outputKey = "items"):
{
  "items": [
    {{range $i, $item := .Collection.items}}
    {{if $i}},{{end}}
    { "id": "{{$item._id}}", "name": "{{$item.name}}" }
    {{end}}
  ]
}

See Collection Mappings for full details including scope, operations, and field mapping rules.

Validation Output Variables

When a Validation Rule runs, its result is stored under {{.Validation.<ruleName>}}. The result always includes _status ("pass" or "fail") plus any properties you configured for the matching outcome.

ExpressionDescription
{{.Validation.authCheck._status}}Rule result: "pass" or "fail"
{{.Validation.authCheck.userRole}}An On Pass / On Fail property named userRole
{{.Validation.authCheck.reason}}An On Fail property named reason
 
// Rule "authCheck": On Pass sets userRole=admin, On Fail sets userRole=guest
{
  "role":   "{{.Validation.authCheck.userRole}}",
  "passed": "{{.Validation.authCheck._status}}"
}

// Conditional branch in body:
{{if eq .Validation.authCheck._status "pass"}}
{ "data": "private content" }
{{else}}
{ "error": "unauthorized" }
{{end}}

See Validation Rules for full details on condition trees and pass/fail properties.

Conditions

Conditions are rules attached to response configurations. A response is selected only when all its conditions evaluate to true. An empty conditions array means "always match".

Condition structure

{
  "source": "query",      // Where to read the value from
  "key": "status",       // Field name within the source
  "operator": "eq",     // Comparison operator
  "value": "active"     // Value to compare against
}

Multiple conditions (AND logic)

All conditions in an array must pass. There is no OR operator — use multiple response configs with different priorities to achieve OR behavior.

"conditions": [
  { "source": "query",  "key": "type", "operator": "eq", "value": "premium" },
  { "source": "header", "key": "Authorization", "operator": "exists" }
]
// Matches only when type=premium AND Authorization header is present

Script output in conditions

// Script bound with outputKey = "pricing" returns {total: 99.99}
{ "source": "script", "key": "pricing.total", "operator": "gt", "value": "50" }

Collection output in conditions

// Spec/operation mapping outputKey = "user" — match only when user was found
{ "source": "collection", "key": "user._status", "operator": "eq", "value": "success" }

// Match on a specific field in the found document
{ "source": "collection", "key": "user.role", "operator": "eq", "value": "admin" }

Validation output in conditions

// Rule "authCheck" — match only when auth rule passed
{ "source": "validation", "key": "authCheck._status", "operator": "eq", "value": "pass" }

// Match on a property set by the validation rule
{ "source": "validation", "key": "authCheck.userRole", "operator": "eq", "value": "admin" }

Body conditions with JSONPath

// Request body: {"order": {"items": [{"sku": "ABC"}], "total": 150}}

// Match on nested field
{ "source": "body", "key": "order.total", "operator": "gt", "value": "100" }

// Match on array element
{ "source": "body", "key": "order.items[0].sku", "operator": "eq", "value": "ABC" }

Examples

Return paginated data

{
  "name": "Paginated list",
  "statusCode": 200,
  "body": "{
    \"data\": [
      {\"id\": \"{{random.uuid}}\", \"name\": \"{{faker.name.full}}\"},
      {\"id\": \"{{random.uuid}}\", \"name\": \"{{faker.name.full}}\"},
      {\"id\": \"{{random.uuid}}\", \"name\": \"{{faker.name.full}}\"}
    ],
    \"page\": {{query.page}},
    \"perPage\": {{query.per_page}},
    \"total\": 250
  }"
}

Content-type negotiation

// Respond differently based on Accept header
{
  "priority": 0,
  "conditions": [{ "source": "header", "key": "Accept", "operator": "contains", "value": "text/xml" }],
  "headers": { "Content-Type": "text/xml" },
  "body": "<user><id>{{path.id}}</id><name>{{faker.name.full}}</name></user>"
}

Echo back the full request

{
  "name": "Debug echo",
  "statusCode": 200,
  "body": "{
    \"path\": \"{{path.id}}\",
    \"queryFilter\": \"{{query.filter}}\",
    \"authHeader\": \"{{header.Authorization}}\",
    \"bodyField\": \"{{body.data.value}}\",
    \"requestTime\": \"{{timestamp.iso}}\"
  }"
}

Version-based routing

// Priority 0: v2 header → return v2 format
{
  "priority": 0,
  "conditions": [{ "source": "header", "key": "X-API-Version", "operator": "eq", "value": "2" }],
  "body": "{\"version\": 2, \"data\": {\"userId\": \"{{path.id}}\"}}"
}

// Priority 10: default → v1 format
{
  "priority": 10,
  "body": "{\"id\": \"{{path.id}}\", \"name\": \"{{faker.name.full}}\"}"
}
