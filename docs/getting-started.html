Getting Started

Install go-virtual, configure it, and start mocking your first API in a few minutes.

Prerequisites

  • Go 1.21+ — for building from source
  • Node.js 18+ — only if building the UI from source
  • Docker — optional, for containerized deployments

Pre-built binaries require no runtime dependencies.

Installation

Build from source

git clone https://github.com/your-org/go-virtual.git
cd go-virtual

# Install all dependencies and build UI + Go binary
make install-deps
make build

# Binary is at ./build/go-virtual
./build/go-virtual --version

Go install

go install github.com/your-org/go-virtual@latest

Docker

docker pull ghcr.io/your-org/go-virtual:latest
docker run -p 8080:8080 -v $(pwd)/data:/app/data ghcr.io/your-org/go-virtual:latest
ℹ️
Binary includes the UI The Go binary embeds the compiled React admin UI. You only need the single binary file to run everything.

Initialize a Workspace

The init command creates a config.yaml and the data/ directory structure in the current folder (or a specified path).

go-virtual init

# Specify a custom path
go-virtual init --path /opt/go-virtual

# Overwrite an existing config
go-virtual init --force

This creates:

.
├── config.yaml          # Main configuration file
└── data/
    ├── specs/           # Uploaded OpenAPI specifications
    ├── responses/       # Response configurations
    ├── operations/      # Operation bindings
    ├── scripts/         # Starlark scripts
    ├── traces/          # Trace history
    ├── stats/           # Statistics
    └── store.json       # Global key-value store

Start the Server

# Start with default config.yaml in current directory
go-virtual serve

# Custom config file
go-virtual serve --config /etc/go-virtual/config.yaml

# Override port
go-virtual serve --port 3000

# Enable TLS
go-virtual serve --tls

# Headless mode (proxy only, no admin UI/API)
go-virtual serve --headless

Once running, you'll see:

{"level":"info","msg":"go-virtual starting","port":8080}
{"level":"info","msg":"Admin UI available","url":"http://localhost:8080/_ui/"}
{"level":"info","msg":"Admin API available","url":"http://localhost:8080/_api/"}
{"level":"info","msg":"Server ready"}
✅
Admin UI Open http://localhost:8080/_ui/ in your browser to access the visual management interface.

Your First Mock API

This walkthrough uses curl. You can do the same steps in the Admin UI.

Step 1 — Upload an OpenAPI 3 spec

cat > /tmp/petstore.yaml <<'EOF'
openapi: "3.0.0"
info:
  title: Pet Store
  version: 1.0.0
paths:
  /pets:
    get:
      operationId: listPets
      summary: List all pets
      parameters:
        - name: status
          in: query
          schema:
            type: string
      responses:
        "200":
          description: A list of pets
  /pets/{id}:
    get:
      operationId: getPet
      summary: Get a pet by ID
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        "200":
          description: A single pet
        "404":
          description: Not found
EOF

curl -X POST http://localhost:8080/_api/specs \
  -H "Content-Type: application/json" \
  -d "{\"name\": \"Pet Store\", \"content\": $(cat /tmp/petstore.yaml | python3 -c 'import sys,json; print(json.dumps(sys.stdin.read()))')}"

Step 2 — Find the operation IDs

SPEC_ID=<id from step 1 response>
curl http://localhost:8080/_api/specs/$SPEC_ID/operations

Note the id field for each operation (e.g., getPet, listPets).

Step 3 — Create a response for getPet

OP_ID=<operation id for getPet>

curl -X POST http://localhost:8080/_api/operations/$OP_ID/responses \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Found",
    "priority": 0,
    "statusCode": 200,
    "headers": {"Content-Type": "application/json"},
    "body": "{\"id\": \"{{path.id}}\", \"name\": \"{{faker.animal.name}}\", \"status\": \"available\"}"
  }'

Step 4 — Create a 404 response for unknown pets

curl -X POST http://localhost:8080/_api/operations/$OP_ID/responses \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Not Found",
    "priority": 10,
    "statusCode": 404,
    "conditions": [{"source": "path", "key": "id", "operator": "eq", "value": "0"}],
    "body": "{\"error\": \"Pet not found\", \"id\": \"{{path.id}}\"}"
  }'

Step 5 — Test your mock

curl http://localhost:8080/pets/42
# {"id":"42","name":"Golden Retriever","status":"available"}

curl http://localhost:8080/pets/0
# {"error":"Pet not found","id":"0"}

Using the Admin UI

The admin UI at /_ui/ provides a visual interface for all management tasks:

PagePurpose
DashboardOverview, request statistics, top operations, trend charts
SpecsUpload YAML/JSON specs, enable/disable, view operations
OperationsBrowse all operations with tag filtering
ResponsesDesign mock responses with drag-and-drop priority, condition builder, template editor
ScriptsWrite and test Starlark scripts with Monaco editor
StoreManage global key-value store entries
SessionsInspect active sessions and their store data
TracesLive-stream and search request traces

CLI Reference

go-virtual serve

FlagShortDefaultDescription
--config-c./config.yamlPath to config file
--port-p8080Override server port from config
--tlsfalseEnable TLS/HTTPS
--headlessfalseDisable admin API and UI (proxy only)
--devfalseServe UI from filesystem (for UI development)

go-virtual init

FlagShortDefaultDescription
--path-p.Directory to initialize
--force-ffalseOverwrite existing config.yaml

Directory Structure

data/
├── specs/
│   └── <spec-id>.json        # Spec metadata + raw content
├── responses/
│   └── <response-id>.json    # Response configurations
├── operations/
│   └── <op-id>.json          # Operation state + script bindings
├── scripts/
│   ├── <script-id>.json      # Script metadata
│   └── <script-id>.star      # Starlark source
├── certs/
│   ├── server.crt             # Auto-generated TLS cert
│   └── server.key             # Auto-generated TLS key
├── traces/                    # Trace history (JSON)
├── stats/                     # Statistics snapshots
└── store.json                 # Global key-value store
⚠️
Atomic writes go-virtual uses a two-file write pattern (write to .tmp, then rename) to prevent data corruption on crashes or restarts.

Docker

Build the image

make docker-build
# Or manually:
docker build -t go-virtual .

Run with persistent data

docker run -d \
  --name go-virtual \
  -p 8080:8080 \
  -v $(pwd)/data:/app/data \
  -v $(pwd)/config.yaml:/app/config.yaml \
  go-virtual

Docker Compose

version: "3.9"
services:
  go-virtual:
    image: ghcr.io/your-org/go-virtual:latest
    ports:
      - "8080:8080"
    volumes:
      - ./data:/app/data
      - ./config.yaml:/app/config.yaml
    restart: unless-stopped

Development Mode

When contributing to go-virtual or customizing the UI:

# Terminal 1 — Go server (auto-reloads with air or manual restart)
make dev-server

# Terminal 2 — Vite dev server with HMR on :5173
make dev-ui

The Vite dev server proxies /_api/ requests to the Go backend. Open http://localhost:5173 for live-reload UI development.
