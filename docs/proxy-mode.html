go-virtual / Proxy Mode

Proxy Mode & Request Signatures

Proxy mode turns go-virtual into a transparent recording proxy — it forwards live traffic to a real backend, captures every response, and replays those exact responses in future offline runs. Request signatures let you fingerprint requests by any combination of path, query, headers, and body fields so each unique variant gets its own recorded mock.

How Proxy Mode Works

When proxy mode is active on a spec, the request pipeline changes:

  Incoming Request
        │
        ▼
  ┌─────────────────────┐
  │  Route matching     │  ← matches operation from OpenAPI spec
  └──────────┬──────────┘
             │
             ▼
  ┌─────────────────────┐
  │  Signature computed │  ← FNV-64a hash of configurable request fields
  └──────────┬──────────┘
             │
      ┌──────┴───────┐
      │              │
  ProxyMode=true   ProxyMode=false
  + BackendURI set   (or no backend)
      │              │
      ▼              ▼
  ┌─────────┐   ┌───────────────────────┐
  │ Forward │   │ Evaluate conditions   │
  │ to real │   │ on response configs   │
  │ backend │   │ (signature match etc) │
  └────┬────┘   └──────────┬────────────┘
       │                   │
       ▼                   ▼
  ┌─────────────────┐  ┌───────────────┐
  │ Record response │  │ Render + send │
  │ as mock with    │  │ matched mock  │
  │ signature cond  │  └───────────────┘
  └────┬────────────┘
       │
       ▼
  Return real response
  to client (pass-through)

Key characteristics:

  • Pass-through while recording — the real backend response is returned to the client immediately; recording is async and does not add latency.
  • Deduplication by signature — the same logical request (same path params, query, headers, body — as defined by the signature config) updates the existing mock rather than creating a duplicate.
  • Zero-edit mocks — recorded responses are immediately usable without any manual editing.
  • Seamless switch — turn off proxy mode and all future requests are served from the captured mocks, no code changes needed.

Setting Up Proxy Mode

Two steps are required: configure the backend URL, then enable proxy mode.

Step 1 — Set the backend URL

curl -X PUT http://localhost:8080/_api/specs/<spec-id>/backend \
  -H "Content-Type: application/json" \
  -d '{"backendUri": "https://api.example.com"}'

The backend URI is the root URL of the real API. go-virtual strips the spec's basePath from the incoming request path before forwarding, so if your spec is mounted at /v2 and the real API doesn't have that prefix, paths resolve correctly.

⚠️
Clearing the URI disables proxy mode If you set backendUri to an empty string, proxy mode is automatically disabled.

Step 2 — Enable proxy mode

curl -X PUT http://localhost:8080/_api/specs/<spec-id>/proxy-mode \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}'

Proxy mode can only be enabled when a backendUri is already set. Attempting to enable it without a backend returns a 400 error.

Via the Admin UI

On the Spec Detail page, the Backend Configuration card lets you paste the backend URI and save it. A Proxy Mode toggle appears once the URI is set. When active, an animated Recording badge (violet, with a radio icon) appears on each operation row.

Verify the setup

curl http://localhost:8080/_api/specs/<spec-id>
# Look for:
# "backendURI": "https://api.example.com",
# "proxyMode": true

Recording & Deduplication

Every request that passes through in proxy mode triggers an async record step after the backend response is returned to the client.

What gets recorded

FieldValue
Name[Recorded] YYYY-MM-DD HH:MM:SS
Tagdefault
Priority1 — just below manually created responses (priority 0)
Condition{"source": "signature", "operator": "eq", "value": "<hash>"}
Status codeExact status code returned by the backend
HeadersBackend headers minus transport-level headers (see Header Handling)
BodyExact response body string
Recorded flagtrue — marked visually in the UI with a ● Recorded badge

Deduplication logic

Before creating a new response config, go-virtual checks whether a config with a signature condition matching this exact hash already exists for the operation:

  • Found — updates the existing config's status code, headers, and body in-place. The ID, name, and creation timestamp are preserved.
  • Not found — creates a new config with a time-based ID (20060102150405-uuid8).

This means re-playing the same request against the backend updates the mock — useful for refreshing stale recordings.

Inspecting recorded responses

# List all response configs for an operation
curl http://localhost:8080/_api/operations/<op-id>/responses

# Recorded entries are identifiable by:
# "recorded": true
# "conditions": [{"source": "signature", ...}]
# "name": "[Recorded] ..."
💡
Edit recorded responses freely Recorded responses are just regular response configs with a recorded: true flag and a signature condition. You can edit the body, change the status code, or add more conditions — it all works exactly the same as manually created responses.

Switching to Replay Mode

Once you have captured the responses you need, disable proxy mode. All future requests are served entirely from the recorded (and any manually created) mock responses.

curl -X PUT http://localhost:8080/_api/specs/<spec-id>/proxy-mode \
  -d '{"enabled": false}'

Or toggle the switch on the Spec Detail page in the UI. The animated "Recording" badge disappears, confirming the server is now serving purely from mocks.

✅
Typical workflow Record → review in Trace Viewer → disable proxy mode → run tests against captured mocks → edit any edge cases manually → commit the data directory to version control.

Request Signatures

A request signature is a deterministic 16-character hex fingerprint computed from configurable parts of an incoming request. It is the key that makes deduplication and exact-match replay possible.

The same logical request — same path params, query string, relevant headers, and body fields — always produces the same hash. A different tenant ID, a different page number, or a different request body produces a different hash and therefore a different recorded mock.

What goes into the hash (defaults)

When no custom signature config is set, the defaults are:

FieldDefaultNotes
Path parametersAll includedSorted alphabetically before hashing
Query parametersAll includedSorted by name, then values sorted per name
HeadersNone includedMust be explicitly listed to include
Request bodyFull body includedCan be narrowed to specific JSON paths

Configuring the Signature

The signature config lives on the operation, not on individual response configs. It applies globally to all requests for that operation.

Signature config fields

FieldTypeDefaultDescription
pathParamsstring[][] (all)Path parameter names to include. Empty array = include all.
queryParamsstring[][] (all)Query parameter names to include. Empty array = include all.
headersstring[][] (none)Header names to include (case-insensitive). Empty array = include none.
includeBodybooltrueWhether to include the request body in the hash.
bodyJsonPathsstring[][] (full body)gjson paths to extract from the body. Empty = use full raw body. Only applies when includeBody is true.

Get & update via API

# Get current config (null = using defaults)
curl http://localhost:8080/_api/operations/<op-id>/signature

# Update
curl -X PUT http://localhost:8080/_api/operations/<op-id>/signature \
  -H "Content-Type: application/json" \
  -d '{
    "pathParams": ["id"],
    "queryParams": [],
    "headers": ["X-Tenant-Id"],
    "includeBody": false
  }'

Reset to defaults

# Set signatureConfig to null to revert to default behavior
curl -X PUT http://localhost:8080/_api/operations/<op-id>/signature \
  -d '{"signatureConfig": null}'

Common configurations

Match only on path ID — ignore query and body

{
  "pathParams": ["id"],
  "queryParams": [],
  "includeBody": false
}
// GET /users/42?debug=true and GET /users/42?lang=en → same signature

Match on tenant header + path ID

{
  "pathParams": ["id"],
  "queryParams": [],
  "headers": ["X-Tenant-Id"],
  "includeBody": false
}
// tenant-a + /users/42 → different signature than tenant-b + /users/42

Match on specific body fields only

{
  "includeBody": true,
  "bodyJsonPaths": ["user.id", "user.role"]
}
// Only user.id and user.role affect the hash; timestamp or metadata fields do not

Match on full request (no configuration needed — this is the default)

{
  "pathParams": [],    // empty = all path params
  "queryParams": [],   // empty = all query params
  "headers": [],       // empty = no headers
  "includeBody": true  // full body
}

How the Hash Is Computed

go-virtual uses FNV-64a (Fowler–Noll–Vo, 64-bit variant) — a fast, non-cryptographic hash that produces a 16-character lowercase hex string.

Input construction

The hash input is built by writing four sections in order into the hash state:

path section: "path:id=42&version=v2|"
query section: "query:filter=active&sort=name|"
headers section: "headers:x-tenant-id=acme|"
body section: "body:{\"quantity\":3}"
→ result: fnv64a → "a1b2c3d4e5f6g7h8"

Determinism rules

  • Map keys are sorted alphabetically before writing — {"b":2,"a":1} hashes the same as {"a":1,"b":2}.
  • Header names are lowercased before comparison — X-Tenant-Id and x-tenant-id are treated identically.
  • Multiple query values per key are sorted before hashing.
  • Body JSON paths (when configured) are sorted and extracted individually, not as a re-serialized object.
💡
Same request = same hash, always The hash is fully deterministic. The same logical request will always produce the same 16-char hex string regardless of the order fields appear in HTTP or JSON, or which server thread handles the request.

Signature Conditions

The signature condition source ("source": "signature") lets you attach a response config to a specific hash value — making it match only requests that produce that exact fingerprint.

Auto-created by proxy recording

When the recorder captures a backend response it automatically writes a condition like this:

{
  "source": "signature",
  "operator": "eq",
  "value": "a1b2c3d4e5f6g7h8"
}

Manually creating a signature condition

You can write a signature condition by hand on any response config — the hash just needs to match what go-virtual would compute for that request. You can find the hash for a specific request in the trace details (the Signature field in the trace metadata).

# Add a manual response that only fires for a specific hash
curl -X POST http://localhost:8080/_api/operations/<op-id>/responses \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Specific tenant response",
    "priority": 0,
    "statusCode": 200,
    "conditions": [
      {"source": "signature", "operator": "eq", "value": "a1b2c3d4e5f6g7h8"}
    ],
    "body": "{\"tenantSpecific\": true}"
  }'

Signature vs other conditions — which wins?

Signature conditions behave like any other condition — they are evaluated in priority order alongside path, query, header, and body conditions. A response config is selected when all its conditions pass. You can mix signature conditions with other condition types:

{
  "conditions": [
    { "source": "signature", "operator": "eq", "value": "a1b2c3d4e5f6g7h8" },
    { "source": "header", "key": "Authorization", "operator": "exists" }
  ]
}
// Matches only when signature matches AND Authorization header is present

Header Handling

go-virtual filters headers in both directions to prevent transport-layer leakage.

Outbound request headers (go-virtual → backend)

These headers from the original client request are not forwarded to the backend:

Host Accept-Encoding Connection Transfer-Encoding Upgrade Proxy-Connection Keep-Alive TE Trailers Proxy-Authorization Proxy-Authenticate

All other request headers are forwarded as-is. This includes Authorization, Content-Type, Cookie, and any custom headers.

Recorded response headers (backend → stored mock)

These backend response headers are stripped before saving to the response config:

Content-Length Transfer-Encoding Content-Encoding Date Age Via Alt-Svc Trailer

All other response headers (e.g., Content-Type, Cache-Control, X-Request-Id, custom headers) are preserved in the mock.

💡
Why strip these headers? Transport-level headers like Content-Length and Transfer-Encoding are managed by Go's HTTP stack and would cause read errors if pre-set. Cache/proxy headers (Age, Via) are meaningless for replay and would expose the real backend.

mTLS for Backend Requests

If the real backend requires mutual TLS (client certificates), configure go-virtual to present a client certificate when making outbound proxy requests.

config.yaml

proxy:
  timeoutSeconds: 30
  insecureSkipVerify: false   # Skip backend TLS verification (dev only)
  mtls:
    certFile:   /certs/client.crt   # PEM client certificate
    keyFile:    /certs/client.key   # PEM private key
    caCertFile: /certs/ca-bundle.crt # CA to verify backend's certificate
OptionTypeDescription
proxy.timeoutSecondsintHTTP client timeout for backend requests (default: 30). Backends that don't respond within this time return a 502.
proxy.insecureSkipVerifyboolSkip TLS certificate verification for the backend. Only for development with self-signed backend certs.
proxy.mtls.certFilestringPath to the PEM client certificate. Must be set together with keyFile.
proxy.mtls.keyFilestringPath to the PEM private key matching certFile.
proxy.mtls.caCertFilestringPath to a custom CA certificate bundle for verifying the backend's server certificate. Falls back to the OS trust store if not set.
⚠️
certFile and keyFile must be set together Setting only one of certFile / keyFile returns an error at server startup. Either set both or neither.

UI Walkthrough

Configuring proxy mode (Spec Detail page)

  1. Navigate to the Spec Detail page — click the spec name on the Specifications page.

  2. Scroll to Backend Configuration — paste the backend URL into the URI input and click Save. The Proxy Mode toggle appears below.

  3. Toggle Proxy Mode on — the toggle turns violet. An animated ● Recording badge appears on every operation row in the operations list.

  4. Make real requests — traffic flows through to the backend and responses are recorded. Watch them appear in the Traces page in real time.

  5. Toggle Proxy Mode off — go-virtual now replays the captured mocks for all future requests.

Configuring the signature (Operation Detail page)

  1. Click an operation row on the Spec Detail page to open the Operation Detail page.

  2. Scroll to Signature Configuration — shows a summary of the current config (or "using defaults").

  3. Click Configure — the panel expands into edit mode with four sections: Path Parameters, Query Parameters, Headers, and Body.

  4. Path Parameters — click All to include every path param, or toggle individual param chips (violet = included, white = excluded).

    Query Parameters — click Include All or type param names one at a time and press Add.

    Headers — type exact header names (e.g., X-Tenant-Id) and press Add. Headers are matched case-insensitively.

    Body — tick the checkbox to include the body. When ticked, an optional JSON Paths input appears — add dot-notation paths (e.g., user.id) to hash only specific fields.

  5. Click Save — the new config takes effect immediately for all subsequent requests. Click Reset to defaults to revert.

Finding a request's signature in traces

Open the Traces page and click any proxy-mode trace. The detail panel shows a Signature field in the metadata section — copy this hash to manually write a matching condition in any response config.

End-to-End Examples

Example 1 — Record a multi-tenant API

An API returns different data per tenant, identified by the X-Tenant header.

# 1. Configure signature to hash only path + tenant header
curl -X PUT http://localhost:8080/_api/operations/op-get-user/signature \
  -d '{
    "pathParams": ["id"],
    "queryParams": [],
    "headers": ["X-Tenant"],
    "includeBody": false
  }'

# 2. Enable proxy mode
curl -X PUT http://localhost:8080/_api/specs/spec-id/backend \
  -d '{"backendUri": "https://real-api.example.com"}'
curl -X PUT http://localhost:8080/_api/specs/spec-id/proxy-mode \
  -d '{"enabled": true}'

# 3. Make requests for both tenants — two separate mocks are recorded
curl http://localhost:8080/users/42 -H "X-Tenant: acme"
curl http://localhost:8080/users/42 -H "X-Tenant: globex"

# 4. Disable proxy mode — each tenant gets its own isolated response
curl -X PUT http://localhost:8080/_api/specs/spec-id/proxy-mode \
  -d '{"enabled": false}'

# 5. Replay: correct response served for each tenant
curl http://localhost:8080/users/42 -H "X-Tenant: acme"    # → acme user data
curl http://localhost:8080/users/42 -H "X-Tenant: globex"  # → globex user data

Example 2 — Capture then refine with manual responses

Record the happy path, then add manual error responses that couldn't be captured from the real API.

# After recording, create a manual 404 that fires before recorded responses
curl -X POST http://localhost:8080/_api/operations/op-get-user/responses \
  -d '{
    "name": "Not Found",
    "priority": 0,
    "statusCode": 404,
    "conditions": [
      {"source": "path", "key": "id", "operator": "startsWith", "value": "invalid-"}
    ],
    "body": "{\"error\": \"User not found\"}"
  }'

# Recorded responses sit at priority 1 — the manual 404 (priority 0) fires first
# for invalid IDs, recorded mock fires for everything else

Example 3 — Refreshing stale mocks

Re-enable proxy mode and replay the same requests to update the recorded responses:

# Re-enable proxy
curl -X PUT http://localhost:8080/_api/specs/spec-id/proxy-mode \
  -d '{"enabled": true}'

# Replay the same requests — recorder finds the existing config by signature
# and updates the body/headers in-place rather than creating duplicates
curl http://localhost:8080/users/42 -H "X-Tenant: acme"
